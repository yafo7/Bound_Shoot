# Unity 2D 多人绳索射击游戏——完整项目开发指令

> 原始需求存档。后续用户已明确要求只交付源码、在Unity Editor中测试、暂不构建或压缩；最新约定以AGENTS.md和WORKLOG.md为准。

## 0. 项目任务

你现在是本项目的 Unity 游戏主程、多人联机工程师和后端工程师。

请直接基于当前工作目录，开发一款完整可运行的 2D 俯视角多人竞技射击 Party Game。

本项目不仅需要实现战斗原型，还需要完成客户端和服务端的全栈闭环：

**注册账号 → 登录 → 游戏大厅 → 选择角色 → 创建/加入房间 → 选择队伍与位置 → 选择地图 → 全员准备 → 开始对战 → 战斗结算 → 返回房间 → 再次开始。**

核心游戏创意：同队玩家通过绳子依次连接，在 2D 竞技场内与对方队伍进行射击战斗。队友之间的物理牵制，以及绳子与地图、尸体之间的交互，是游戏最重要的特色。

参考游戏：

- 《链在一起》（Chained Together）：多人连接、物理拉扯、互相牵制。
- 《荒野乱斗》（Brawl Stars）：俯视角射击、简洁战斗、地图道具。

两款游戏仅作为机制参考，不需要复制其美术。

### 开发原则

1. 优先做出真实可运行、可联机、可测试的游戏，不要停留在文档和伪代码。
2. 保证前后端职责清晰，核心战斗采用服务器权威模式。
3. 使用简洁的占位美术，但 UI 应清晰、协调且完整。
4. 保留模块化结构，便于以后增加地图、武器和道具。
5. 核心规则不得擅自更改。
6. 对未明确的数值，可以使用合理的临时值，但必须集中配置，便于修改。
7. 按阶段开发和验证，不要在基本联机未完成时堆积大量游戏内容。
8. 如果现有工作目录已有项目或资源，先检查并尽量复用，不要随意覆盖。

# 第一部分：技术架构

## 1. 技术选型

### 游戏客户端

- Unity 2022.3 LTS
- C#
- 2D 物理系统 Physics2D
- 2D 正交摄像机
- Unity UI / TextMeshPro
- Windows PC 客户端

### 多人网络

- Netcode for GameObjects
- Unity Transport
- Server Authoritative 模式
- 独立 Dedicated Server

使用与实际 Unity 2022.3 编辑器兼容的 Netcode 和 Transport 版本，安装前检查官方兼容性。

### 后端

- Node.js
- TypeScript
- Express
- WebSocket（ws）用于大厅和房间实时状态通知
- SQLite 数据库存储账号、角色配置、战绩
- 密码使用 Argon2id 或 bcrypt 安全哈希
- 认证采用短期 Access Token + 可撤销的 Refresh Token

### 部署

- 客户端：Windows 可执行程序
- 游戏服务器：Linux Unity Dedicated Server
- 业务服务器：Node.js
- 数据库：SQLite
- 部署环境：用户自有 Ubuntu 云服务器

不依赖 Unity Relay、Unity Lobby 等付费或托管服务。

## 2. 服务架构

系统拆分为三部分：

**A. Unity Client**

负责：
- 登录与注册界面
- 游戏大厅和房间 UI
- 角色选择
- 地图与座位选择
- 玩家输入
- 战斗画面
- 本地特效与音效
- 结算展示

**B. Node.js Backend**

负责：
- 用户注册与登录
- Token 管理
- 用户资料
- 角色外观保存
- 房间创建、加入、退出
- 队伍及座位管理
- 地图选择
- 准备状态
- 房主权限
- 启动与管理对战服务器实例
- 游戏会话凭证
- 对战结果存储
- 历史战绩查询

**C. Unity Dedicated Server**

负责：
- 创建战斗世界
- 玩家出生与位置同步
- 移动与 2D 物理
- 绳索物理
- 子弹生成及命中
- 伤害和生命值
- 武器与道具
- 死亡、尸体拖拽、复活
- 战斗计时
- 胜负判定
- 权威结算结果

客户端只发送移动方向、瞄准方向、攻击、使用道具等操作意图。

服务器负责验证并执行。

禁止让客户端直接决定生命值、伤害、道具获取、击杀或胜负。

## 3. 对战实例管理

每个正在运行的房间对应一个游戏对战实例。

Node.js 后端负责：

1. 接收房主的开始游戏请求。
2. 检查所有玩家是否满足开战条件。
3. 预留一个空闲的服务器端口。
4. 启动或分配 Unity Dedicated Server 实例。
5. 向游戏服务器传递 Match ID、地图、队伍和玩家座位信息。
6. 等待服务端报告 Ready。
7. 给玩家发放短期、不可重复使用的对战连接凭证。
8. 将服务器地址和端口发送给对应客户端。
9. 客户端完成连接后进入同一场战斗。
10. 对战结束后接收权威结算信息，写入数据库，清理战斗实例。

第一阶段允许限制同时运行的对战实例数量，例如 1–2 个，具体根据服务器资源配置。

当容量不足时，应明确提示“服务器繁忙”，不能重复占用端口或让新对战错误连接到其他房间。

需要支持本地开发时手动启动游戏服务器，以及正式部署时由后端管理 Linux 服务端进程。

# 第二部分：账号系统

## 4. 注册

游戏启动后显示登录界面。

支持：

- 注册
- 登录
- 记住登录状态
- 退出登录

注册字段：

- 用户名
- 密码
- 确认密码

用户名必须唯一。

注册成功后进入游戏大厅，首次创建默认角色资料。

密码不可明文保存，数据库只保存安全哈希。

需要完成基础输入校验、重复用户名检查和错误提示。

## 5. 登录

玩家输入用户名和密码后，客户端调用后端认证接口。

登录成功后：

- 获取身份凭证。
- 获取用户资料。
- 获取角色外观配置。
- 进入主大厅。

客户端重新启动时，如果本地存在有效登录凭证，可自动恢复登录状态。

Access Token 过期时应尝试安全刷新，刷新失败则返回登录界面。

避免在日志中输出密码、完整 Token 或其他敏感凭证。

同一账号不允许同时占用两个正在对战的玩家位置。

## 6. 用户数据

每个账号至少包含：

- User ID
- Username
- Display Name
- Password Hash
- 注册时间
- 角色外观配置
- 总对局数
- 总胜利数
- 总击杀
- 总死亡

用户战绩必须由游戏服务器提交的有效结算结果更新，而不是客户端直接上传分数。

# 第三部分：游戏大厅与角色选择

## 7. 主大厅

玩家成功登录后进入主大厅。

主要功能：

1. 当前玩家信息。
2. 角色外观选择。
3. 创建房间。
4. 输入房间号加入房间。
5. 查看基础个人战绩。
6. 退出账号。

UI 风格以清晰、轻量、卡通化为主。

无需复杂动画、商城和付费系统。

## 8. 角色选择

角色之间没有任何属性差异。

角色外观只影响：

- 颜色
- 基础形象
- 装饰

第一版使用简单的 2D 图形或 Sprite 作为角色，提供至少 4 种明显不同的外观。

玩家可以预览和选择角色。

角色选择保存到账号资料，进入房间和战斗时同步给其他玩家。

武器决定角色属性，外观不影响生命值、速度、伤害或其他数值。

# 第四部分：多人房间系统

## 9. 创建房间

在大厅点击“创建房间”。

创建成功后：

- 生成唯一房间 ID 和便于分享的房间号。
- 创建者成为房主。
- 房主自动进入房间。
- 房间默认模式为 2v2。
- 房间默认地图为 Arena_01。

房主可设置：

- 2v2
- 3v3
- 4v4
- 地图

一个房间最多支持 8 名玩家。

第一版完整实现 2v2，架构必须支持扩展到 3v3 和 4v4。

## 10. 加入房间

玩家输入房间号后加入房间。

需要处理：

- 房间不存在
- 房间人数已满
- 房间正在战斗
- 重复加入
- 网络异常

加入房间后，所有成员应实时看到最新的玩家列表。

## 11. 房间座位系统

房间中有两支队伍：

- 蓝队
- 红队

玩家可以自由选择队伍和座位。

**注意：座位不仅决定队伍，也决定玩家在绳子上的连接顺序。**

例如：

2v2：

蓝队：A1—A2

红队：B1—B2

3v3：

蓝队：A1—A2—A3

红队：B1—B2—B3

4v4：

蓝队：A1—A2—A3—A4

红队：B1—B2—B3—B4

每个人只和连接顺序上相邻的队友通过绳子连接，不采用所有玩家相互连接的网状结构。

玩家可以选择未被占用的位置。

服务端必须验证座位占用，避免多个玩家同时抢占同一位置。

房间内显示：

- 玩家名称
- 角色外观
- 所属队伍
- 绳索顺序
- 是否准备

建议界面中直接使用连线展示每队的连接关系。

## 12. 地图选择

由房主选择本局地图。

第一版先完整制作 Arena_01。

后续支持更多地图时，只需加入地图数据和场景，不需要重写房间逻辑。

地图 ID、名称、预览图等应使用统一配置。

如果地图尚未完成，UI 不允许将其作为可开战地图。

## 13. 准备与开战

玩家选好队伍位置后点击“准备”。

房主可以点击“开始游戏”。

开战条件：

1. 两队人数满足当前模式。
2. 所有玩家都有唯一座位。
3. 所有人均已准备。
4. 房主点击开始。
5. 对战服务器资源可用。

初版 2v2 必须恰好四名玩家全部准备才可开战。

更换队伍、位置或地图时，受影响的准备状态需要重新确认。

游戏开始后，房间进入 InGame 状态。

客户端连接战斗服务器，加载所选地图。

待玩家完成加载后，统一进行 3 秒倒计时，然后开始战斗。

## 14. 退出与异常

需要实现：

- 房主离开时自动移交房主。
- 普通成员离开后释放座位。
- 玩家离开或掉线后同步房间状态。
- 玩家掉线重连时尽量恢复原房间及位置。
- 正在对战的房间禁止其他账号随意加入战局。

游戏结算后，所有正常在线玩家返回原房间，保留队伍与座位，清除准备状态，等待下一局。

# 第五部分：核心战斗

## 15. 游戏模式

游戏采用 2D 俯视角。

基础模式：

- 2v2。
- 3v3 和 4v4 作为后续扩展。
- 玩家分成红蓝两队。
- 每队玩家被绳子依次连接。
- 双方争夺地图上的武器和道具。
- 在 180 秒内击败敌方队伍。

每名玩家单独计算击杀和死亡次数。

## 16. 控制方式

- WASD：角色移动
- 鼠标移动：瞄准
- 鼠标左键：开火或近战攻击
- E：使用道具

角色始终面向鼠标瞄准方向。

摄像机为 2D 正交俯视视角。

可以让摄像机跟随本地玩家，但必须确保能够看清周围地形、绳索和附近队友。

移动采用 Rigidbody2D，角色需要与墙体、柱子发生真实碰撞。

# 第六部分：绳索系统

## 17. 绳索连接

这是游戏最核心的机制，必须重点实现。

同队玩家按照房间内确定的顺序，用绳子连接。

每两个相邻角色之间是一段绳索。

绳索具有：

- 最大长度
- 弹性
- 回拉力
- 阻尼
- 可配置的物理参数

正常情况下，玩家可以自由移动。

当玩家间距离超过绳索允许的最大长度后，产生物理拉力。

例如：

玩家 A 往左走，玩家 B 往右走。

两人超过绳索最大长度后，绳子绷紧并产生拉扯。

绳索必须实际影响玩家运动，不能只有视觉连线。

## 18. 绳子与地图交互

地图中存在墙壁、柱子和障碍物。

需要逐步实现：

1. 绳子与普通墙体和柱子产生有效的阻挡交互。
2. 玩家从障碍物两侧通过时，绳子可能绕过障碍。
3. 绳子被障碍阻挡时会限制队友移动。
4. 玩家回退或移动到合适位置时，可以解开障碍处的绳子。
5. 不允许绳子长期无故卡死、无限抖动或造成角色瞬移。

优先完成稳定的绳索长度限制，再实现障碍绕行和解绕。

可使用 Physics2D、DistanceJoint2D 和自定义绳索约束逻辑组合实现。

复杂障碍绕行不必采用大量刚体链节模拟，可以使用绳索折点与物理约束方案，但必须让实际拉扯效果和可见绳索保持一致。

## 19. 绳索联机同步

服务器负责物理计算。

客户端接收：

- 玩家位置
- 角色朝向
- 绳索状态
- 绳索折点或其他必要的视觉数据

客户端可以插值平滑表现。

禁止多个客户端独立计算最终绳索位置并互相覆盖。

需要特别测试：

- 两人朝相反方向奔跑。
- 一人静止，另一人冲刺。
- 两人从柱子不同方向绕行。
- 3v3 中间玩家受到两侧队友的拉扯。
- 尸体被存活队友拖动。

# 第七部分：武器系统

## 20. 武器基础规则

地图上会随机散落武器。

出生点和中心战斗区之间设有补给点，武器和道具在补给点附近富集出现。

玩家出生时处于空手状态：

- 基础生命值为 3。
- 暂时没有远程武器。
- 可以移动、拾取武器与道具。

### 最重要的规则：武器锁定

**玩家一旦捡取武器，本次生命期间便不能更换武器。**

具体规则：

1. 空手状态可以拾取任意武器。
2. 拾取成功后立即装备。
3. 武器改变角色最大生命值、攻击力、射程及攻击方式。
4. 已经持有武器时，不能再次拾取其他武器。
5. 即使路过其他武器，也不能替换。
6. 玩家死亡后失去武器。
7. 玩家复活后重新进入空手状态，可以再次拾取武器。

不要实现传统射击游戏的自由换枪、背包或双武器系统。

## 21. 武器类型

初始武器：

| 武器 | 最大生命值 | 单次攻击伤害 | 攻击距离 |
|---|---:|---:|---|
| 狙击枪 | 1 | 4 | 无限 |
| 手枪 | 3 | 1 | 近 |
| AK | 3 | 2 | 远 |
| 匕首 | 5 | 3 | 近战 |

武器设计重点是形成鲜明的战斗定位。

### 狙击枪

- 伤害高。
- 角色仅 1 点血。
- 射程无限，实际受地图边界和障碍物遮挡。
- 攻击频率低。

### 手枪

- 基础生命值为 3。
- 伤害较低。
- 射程较近。
- 攻击频率适中。

### AK

- 基础生命值为 3。
- 伤害为 2。
- 射程较远。
- 支持连续射击。

### 匕首

- 生命值为 5。
- 近战攻击。
- 伤害为 3。
- 需要接近敌人才能有效攻击。

以上是正式的初始数值。

射击间隔、弹速、子弹范围、近战判定范围先使用合理的测试值，后续再平衡。

武器伤害统一采用整数生命值系统。

首次拾取武器时，将角色生命值设为对应武器的最大生命值。

武器装备后，生命值上限保持不变，直到角色死亡并重新复活。

# 第八部分：道具系统

## 22. 道具分类

道具分为：

1. 状态道具
2. 使用道具

所有道具以可拾取物体的形式出现在地图上。

部分道具在补给区内有较高刷新概率。

## 23. 状态道具

拾取后立即产生效果，不进入背包。

### 23.1 绳索收缩

使敌方队伍的每段绳索最大长度临时缩短。

例如缩短到原长度的 65%。

玩家之间更容易互相拉扯。

默认持续 10 秒，结束后恢复原始参数。

### 23.2 绳索延长

使己方队伍每段绳索最大长度临时增加。

例如增加到原长度的 150%。

能够扩大玩家活动范围。

默认持续 10 秒。

### 23.3 护盾

拾取后立即获得 1 点护盾值。

护盾相当于额外生命值，优先于生命值抵挡伤害。

第一版设置护盾最多 1 点，避免无限堆叠。

### 23.4 弹性强化

使双方队伍的绳索回拉力临时增加到正常值的 3 倍。

注意：**影响双方队伍，而不是只强化拾取者所在队伍。**

持续时间暂定 10 秒。

### 23.5 血包

拾取后立即恢复 1 点生命值。

不得超过当前武器对应的最大生命值。

空手状态则不得超过基础最大生命值。

## 24. 使用道具

拾取后进入玩家道具槽。

- 每个玩家最多携带一个使用道具。
- 按 E 使用。
- 使用后道具消耗。
- 再次拾取新的使用道具时，直接覆盖旧道具。
- 死亡后未使用的道具清空。

### 24.1 冲刺装置

拾取后可以按 E 进行一次快速冲刺。

冲刺方向优先使用当前 WASD 移动方向，未输入时使用面朝方向。

冲刺时依然受到绳子物理限制和地图碰撞影响。

不提供默认无敌效果。

### 24.2 炸弹

按 E 在当前角色位置放置炸弹。

放置后经过 3 秒发生爆炸。

爆炸具有范围伤害。

初始测试数值：

- 爆炸伤害：2
- 爆炸半径：可配置

第一版关闭友军伤害，但敌方可以受到爆炸伤害。

## 25. 问号盒子

地图生成随机问号道具盒。

玩家拾取后，随机得到一种已实现的道具。

如果抽中状态道具，立即使用。

如果抽中使用道具，放入道具槽，按已有覆盖规则执行。

随机池和概率必须可配置。

## 26. 道具配置

所有道具需要支持：

- 名称
- 类型
- 图标
- 作用目标
- 效果
- 持续时间
- 刷新概率
- 可用状态

持续状态效果由服务器管理。

同一种临时状态效果重复获得时，默认刷新持续时间，不无限叠加。

不同效果同时存在时应正确计算，不得永久污染基础绳索参数。

# 第十部分：死亡、尸体与复活

## 29. 死亡机制

生命值归零时，角色死亡。

死亡后：

- 角色失去控制权。
- 不能开火。
- 不能使用道具。
- 当前武器消失。
- 携带的使用道具清空。
- 临时增益按死亡规则清除。
- 原位置生成或切换为可拖动尸体。
- 尸体仍然处于原队伍的绳索连接关系中。

尸体必须具有物理实体。

队友可以通过绳子拖拽尸体。

例如 A 死亡，B 存活。

A 的尸体仍然连接 B。

B 可以拖着 A 的尸体继续移动、射击或前往复活点。

3v3 和 4v4 中，死亡的中间玩家不能导致绳索链断开。

## 30. 复活区域

中心战斗区域的上、下两侧设置复活点。

任意队伍都可以使用这两个复活区域。

玩家死亡后，队友需要通过绳索拖动尸体，把尸体带到复活点。

当尸体处于复活区域内：

- 开始 5 秒倒计时。
- 显示复活进度。
- 如果尸体离开区域，倒计时重置。
- 满 5 秒后复活成功。

复活后：

- 玩家恢复操作。
- 生命值恢复为基础 3 点。
- 角色处于空手状态。
- 可以重新捡取武器。
- 保持原本的队伍和绳索连接位置。
- 恢复到可战斗状态。

复活时可以给予短暂出生保护，例如 2 秒，防止在复活区域立刻被击杀；该值必须可配置。

## 31. 团队全灭

当一支队伍所有成员同时处于死亡状态时，该队立即失败。

如果仍然存在存活的队友，即使其他队友死亡，也可以继续战斗并尝试复活。

# 第十一部分：战斗规则与结算

## 32. 回合规则

单回合总时长：180 秒。

开始时服务器统一倒计时。

屏幕上方显示剩余时间。

### 胜利条件

第一优先级：敌方队伍全部死亡。

若一方全灭，另一方立即获胜。

如果倒计时结束，双方仍有存活人员：

1. 比较存活人数。
2. 存活人数多的一方获胜。
3. 若相同，比较存活成员的剩余总生命值。
4. 若仍相同，判为平局。

对战结果必须由游戏服务器计算。

## 33. 玩家统计

每名玩家记录：

- 击杀次数
- 死亡次数
- 造成伤害
- 获得胜利或失败
- 当前武器

击杀归属由服务器根据最后一次有效致命伤害确定。

如果伤害来自场景等非玩家来源，可以不计入个人击杀。

同一玩家在一场比赛中可以多次死亡和复活。

每次真正死亡都应正确增加死亡次数，不能因为同一死亡事件重复处理而多次计数。

## 34. 结算页面

比赛结束后显示：

- 蓝队胜利 / 红队胜利 / 平局
- 本局地图
- 游戏时长
- 每名玩家名称
- 角色形象
- 所属队伍
- 击杀
- 死亡
- 造成伤害

提供：

**返回房间**

所有仍在线的玩家在结算后返回原房间。

房间成员和位置保留，准备状态重置。

可以再次开始下一局。

对局结果写入数据库。

# 第十二部分：联网与异常处理

## 35. 服务器权威同步

使用服务器权威模式管理：

- 玩家真实位置
- Rigidbody2D 物理
- 绳索约束
- 玩家生命值
- 道具生成与拾取
- 武器获取和锁定
- 攻击冷却
- 子弹命中
- 死亡与复活
- 回合计时
- 战斗结果

客户端不能直接提交最终状态，只能发出操作请求。

客户端显示使用插值和必要的本地预测来优化体验，但服务端始终具有最终决定权。

初始可以采用约 30Hz 的服务器物理与逻辑更新，并对网络同步频率进行独立配置。

不要在每帧无条件广播大量完整物体状态。

## 36. 身份认证与战斗连接

业务登录凭证与游戏连接凭证分开。

流程：

1. 玩家正常登录账号。
2. 通过后端加入并准备房间。
3. 后端创建 Match。
4. 后端生成短期有效、绑定 Match ID 和玩家座位的一次性连接凭证。
5. Unity 客户端携带该凭证连接游戏服务器。
6. 游戏服务器在连接批准过程中验证凭证。
7. 验证成功后生成对应玩家的 NetworkObject。

不可通过修改客户端传入的 User ID、Team ID 或 Seat Index 冒充其他玩家。

敏感凭证不得写死在 Unity 客户端代码中。

## 37. 掉线与重连

实现基础异常处理。

房间中断线：

- 保留短暂重连窗口。
- 恢复连接后同步最新房间状态。
- 超时后释放房间位置。
- 必要时重新选座和准备。

对战中断线：

- 暂时保留玩家实体和原绳索连接。
- 断线期间不接受新的角色操作输入。
- 提供约 20 秒的重连宽限期。
- 玩家重新登录后，可申请新的对战连接凭证恢复原角色。
- 超时后，按死亡处理，不得让角色或绳索处于无效状态。

所有断线和重连时间均使用可配置参数。

需要防止同一账号重复进入、旧客户端重新接管、重复结算。

## 38. 网络失败处理

至少处理：

- 登录服务器不可用。
- 房间号错误。
- 加入房间超时。
- 战斗服务器启动失败。
- 玩家连接超时。
- 游戏服务器意外退出。
- 客户端断线。
- 对战结算重复提交。

游戏服务器异常终止时，需要明确通知玩家并安全结束该场比赛。

不要将异常中止的比赛错误记录为正常胜负。

账号基础信息。

角色外观配置。

登录会话与刷新凭证。

房间 ID、房间号、房主、模式、地图和状态。

成员、队伍、绳索座位、准备状态。

比赛 ID、房间、地图、开始时间、结束时间、胜负和状态。

- 所有 SQL 使用参数化查询。
- SQLite 启用适当的事务和 WAL 配置。
